# 화물운송플랫폼 설계 문서

2026-11-02 · 원본: [Claude 문서](https://claude.ai/artifact/LENc6NFFQ9vxeBMQ7rdpgb) (팀 댓글과 수정은 원본에서 하고, 확정되면 이 파일을 갱신한다)

## 1. 개요

화주가 운송 의뢰를 올리고, 차주가 의뢰를 골라 수락해 운송한 뒤, 화주가 수령을 확인하면 플랫폼이 보관하던 운임을 차주에게 지급하는(에스크로) 화물 중개 웹 플랫폼입니다. 팀 5명이 한 달 동안 만드는 포트폴리오용 프로젝트이며, 실제 서비스는 하지 않습니다.

**만드는 이유**: 화물중개플랫폼의 핵심 흐름(오더 등록, 매칭, 운송 진행, 정산)을 직접 설계하고 구현해서 포트폴리오로 설명할 수 있는 결과물을 만드는 것입니다. 시장 조사는 [화물운송시스템 조사 종합 정리](https://claude.ai/artifact/FswnBgdYuEkTQuZu7o2Ney)에 있습니다.

**목표**

- 화주, 차주, 관리자 세 역할의 흐름이 처음부터 끝까지 실제로 동작한다
- 면접에서 설명할 핵심 세 가지를 제대로 구현하고 테스트로 증명한다: 오더 상태 흐름, 동시 수락 방지, 추천 운임 계산
- 5명이 AI 도구를 써도 코드 구조와 스타일이 하나로 유지된다

**하지 않는 것**

- 실제 결제, 세금계산서, 전자인수증 같은 법적 절차
- 실시간 위치 추적, 화물차 전용 경로
- 모바일 앱 (반응형 웹만 만든다)
- 배포와 운영 (각자 로컬에서 실행)

**실패로 보는 경우** (기능이 돌아가더라도)

- 상태가 규칙을 벗어나 바뀐다 (예: 배차 전 오더가 운송완료가 됨)
- 한 오더를 두 차주가 동시에 수락한다
- 도메인마다 코드 방식이 달라서 한 프로젝트로 보이지 않는다

## 2. 사용자와 전체 흐름

역할은 화주, 차주, 관리자 세 가지이고, 한 회원 테이블에서 `role` 값으로 구분합니다. 한 계정은 한 역할만 갖습니다.

| 역할 | 하는 일 |
| --- | --- |
| 화주 | 오더 등록(운임 입력과 더미 결제), 내 오더 조회, 배차 전 취소(환불), 수령 확인 또는 문제 신고 |
| 차주 | 차량 등록, 차종별 의뢰 목록 조회, 수락, 상차 완료, 하차 완료, 내 운송·정산 내역 |
| 관리자 | 운임 단가표 관리, 분쟁 처리, 전체 오더 관리(배차 후 취소 포함), 결제 내역 조회 |

**오더 하나의 일생**

1. 화주가 출발지·도착지, 화물 정보, 희망 배송일과 상차 희망 시각, 요구 차종, 운임을 입력해 오더를 등록한다. 입력 중에 추천 운임이 표시된다. 등록할 때 운임을 결제하면 플랫폼이 보관하고, 결제된 오더만 의뢰 목록에 오른다.
2. 차주는 '내 차량 맞춤' 탭이나 차종별 탭에서 오더를 보고 수락한다. 차종이 맞지 않으면 경고창이 뜨고, 확인하면 수락된다.
3. 차주가 상차 완료, 하차 완료를 차례로 누른다.
4. 화주가 수령을 확인한다. 24시간 안에 확인하지 않으면 자동으로 확인 처리되고, 문제가 있으면 신고해 관리자에게 넘긴다.
5. 운송완료가 되는 순간 보관 중인 운임이 차주에게 지급된다. 결제와 지급은 더미라 실제 돈은 오가지 않는다.

**오더 입력 항목** *(제안)*

| 구분 | 필수 | 선택 |
| --- | --- | --- |
| 상차지 | 주소, 상세주소, 현장 담당자 이름·연락처 | |
| 하차지 | 주소, 상세주소, 수령인 이름·연락처 | |
| 일정 | 상차 희망 일시(`pickup_at`), 도착 희망 일시 | |
| 화물 | 품목명, 화물 종류(일반·파렛트·기계·설비·건자재·가구·가전·기타), 중량(kg), 수량과 포장 단위(박스·파렛트·개) | 크기(가로·세로·높이 cm), 취급 주의(파손주의·쌓기 금지) |
| 운송 | 요구 차종, 운임 | 적재함 형태(카고·윙바디·탑차·냉장냉동), 상하차 방법(지게차 / 수작업), 요청사항 메모 |

- 추천 차종은 중량 기준으로만 계산하고, 크기는 차주에게 보여만 줍니다.
- 상하차 방법이 수작업이면 수작업 할증이 붙습니다.
- 적재함 형태는 첫 버전에서 정보로만 보여줍니다. 차량 등록과 매칭에 쓸지는 나중에 정합니다. *(보류)*
- 개인정보 보호: 의뢰 목록에는 주소를 시·구까지만 보여주고, 상세주소와 담당자 연락처는 배차완료 이후 배정된 차주에게만 보여줍니다.

## 3. 오더 상태 흐름

오더는 7개 상태 중 하나이고, 아래 표에 없는 전이는 서버가 모두 거부합니다. 상태 변경은 `Order` 엔티티의 메서드(예: `order.accept(driver)`)로만 하고, 각 메서드가 현재 상태와 요청자를 검사합니다. 서비스에서 `setStatus()`를 직접 부르지 않습니다.

```
            ┌──────── 차주 배차 취소 ────────┐
            ▼                               │
 [등록됨 · 결제·보관] ─차주 수락→ [배차완료] ─상차 완료→ [운송중] ─하차 완료→ [수령확인대기] ─수령 확인 / 24시간→ [운송완료 · 차주에게 지급]
      │                      │                                            │                                  ▲
   화주 취소              관리자 취소                                   문제 신고                        관리자 지급 처리
      ▼                      ▼                                            ▼                                  │
 [취소됨 · 화주에게 환불] ◀───────── 관리자 취소 처리 ─────────── [분쟁 · 계속 보관] ────────────────────────┘
```

| 현재 상태 | 행동 | 누가 | 다음 상태 | 결제 |
| --- | --- | --- | --- | --- |
| (없음) | 오더 등록 + 결제 | 화주 | 등록됨 `REGISTERED` | 보관중 |
| 등록됨 `REGISTERED` | 수락 | 차주 | 배차완료 `ASSIGNED` | — |
| 등록됨 `REGISTERED` | 취소 | 화주(본인 오더), 관리자 | 취소됨 `CANCELLED` | 환불 |
| 등록됨 `REGISTERED` | 운임·내용 수정 | 화주 | 등록됨 (그대로) | 운임이 바뀌면 차액 결제 또는 부분 환불 |
| 배차완료 `ASSIGNED` | 상차 완료 | 배정된 차주 | 운송중 `IN_TRANSIT` | — |
| 배차완료 `ASSIGNED` | 배차 취소(사유 필수) | 배정된 차주 | 등록됨 `REGISTERED` (차주 해제) | 계속 보관 |
| 배차완료 `ASSIGNED` | 취소 | 관리자만 | 취소됨 `CANCELLED` | 환불 |
| 운송중 `IN_TRANSIT` | 하차 완료 | 배정된 차주 | 수령확인대기 `AWAITING_CONFIRM` | — |
| 수령확인대기 `AWAITING_CONFIRM` | 수령 확인 | 화주 | 운송완료 `COMPLETED` | 차주에게 지급 |
| 수령확인대기 `AWAITING_CONFIRM` | 24시간 경과 | 시스템(스케줄러) | 운송완료 `COMPLETED` | 차주에게 지급 |
| 수령확인대기 `AWAITING_CONFIRM` | 문제 신고 | 화주 | 분쟁 `DISPUTED` | 계속 보관 |
| 분쟁 `DISPUTED` | 지급 처리 | 관리자 | 운송완료 `COMPLETED` | 차주에게 지급 |
| 분쟁 `DISPUTED` | 취소 처리 | 관리자 | 취소됨 `CANCELLED` | 환불 |

**규칙**

- 상태가 바뀔 때마다 `order_status_history`에 이전 상태, 다음 상태, 행동한 사람, 시각, 메모(신고 사유 등)를 남깁니다. 관리자 분쟁 화면과 오더 상세의 이력이 이 표를 씁니다.
- 자동 확인 기준 시각은 하차 완료 시각입니다. 스케줄러는 10분마다 돌고, 24시간은 설정값(`app.order.auto-confirm-hours`)으로 둡니다. 시연할 때는 1분 등으로 줄여 보여줄 수 있습니다.
- 수정은 등록됨 상태에서만 됩니다. 희망 배송일이 지났는데 아직 등록됨이면 화주 오더 목록에 '미배차' 표시를 보여주고 운임 수정을 권합니다. 별도 상태는 두지 않습니다.

**차주 배차 취소** *(제안)*

- 차주는 배차완료 상태에서만 직접 취소할 수 있고, 사유를 반드시 적습니다. 오더는 등록됨으로 돌아가 의뢰 목록에 다시 나타나고, 배정 차주는 비워집니다.
- 상차 희망 시각 2시간 전부터는 직접 취소할 수 없고, 관리자에게 요청해야 합니다. 2시간은 설정값(`app.order.driver-cancel-cutoff-hours`)으로 둡니다.
- 운송중부터는 차주가 취소할 수 없습니다. 문제가 생기면 관리자가 처리합니다.
- 취소는 상태 이력에 사유와 함께 남기고, 화주는 오더 상세에서 '차주가 배차를 취소했습니다' 표시를 봅니다. 차주별 취소 횟수는 관리자 회원 관리에서 볼 수 있습니다.

**에스크로 결제** *(팀 결정: 에스크로, 등록 시 결제 / 제안: 세부 규칙)*

- 화주는 오더를 등록할 때 운임을 결제합니다. 플랫폼이 그 돈을 보관하고, 운송완료가 되면 차주에게 지급하며, 취소되면 화주에게 환불합니다. 결제·지급·환불은 모두 더미입니다. 차주가 수락할 때 결제하는 방식은 '결제대기' 상태와 기한 처리가 늘어나고 차주가 확정을 기다려야 해서 택하지 않았습니다.
- 결제는 `payment` 테이블에 오더당 하나로 둡니다. 결제 상태는 `HELD`(보관중) → `RELEASED`(지급완료) 또는 `REFUNDED`(환불완료)만 있고, 한 번 지급·환불된 결제는 다시 바뀌지 않습니다.
- 오더 상태 변경과 결제 상태 변경은 한 트랜잭션에서 처리합니다. 하나만 바뀌고 다른 하나가 실패하면 둘 다 되돌립니다.
- 등록됨 상태에서 운임을 올리면 차액을 추가 결제하고, 내리면 차액을 환불합니다. 결제 내역은 `payment_transaction`에 건별(결제·추가결제·부분환불·지급·환불)로 남깁니다.
- 더미 결제는 `PaymentGateway` 인터페이스 뒤에 둡니다. 지금은 항상 성공하는 `DummyPaymentGateway`를 쓰고, 나중에 토스페이먼츠 같은 실제 PG 테스트 모드로 바꿀 수 있게 합니다.
- 테스트: 모든 취소 경로가 환불로, 모든 완료 경로가 지급으로 끝나는지, 자동 확인과 화주 확인이 동시에 일어나도 지급이 한 번만 되는지 확인합니다.

## 4. 운임과 추천 운임

최종 운임은 화주가 직접 입력하고, 플랫폼은 거리와 차종으로 계산한 추천 운임을 참고용으로 보여줍니다. 차주는 운임을 제안할 수 없고 수락만 합니다.

**계산 순서**

1. 거리: 출발지·도착지 주소를 좌표로 바꾸고 길찾기 API로 도로 거리(km)를 구합니다. 주소 검색은 다음(카카오) 우편번호 서비스, 좌표 변환과 거리는 카카오 로컬·카카오모빌리티 길찾기 API를 제안합니다. API 키가 없거나 호출이 실패하면 두 좌표의 직선거리(하버사인) × 1.3으로 대신합니다.
2. 차종: 중량(kg)을 담을 수 있는 가장 작은 차종을 고릅니다. 이 값이 화주 화면의 '요구 차종' 기본값이 되고, 화주는 바꿀 수 있습니다.
3. 운임: 아래 공식에 넣고, 1,000원 단위로 반올림합니다.

```
추천 운임 = (기본요금 + 거리(km) × km당 단가) × (1 + Σ 할증률)
```

할증은 첫 버전에서 네 가지이고, 여러 개가 해당하면 할증률을 더합니다. 시각 판정을 위해 오더는 희망 배송일과 상차 희망 시각(시 단위)을 합친 `pickup_at`(DATETIME)을 갖습니다. *(팀 결정: 시각도 받기)*

| 할증 | 판정 기준 |
| --- | --- |
| 야간 | 상차 희망 시각이 22시~06시 |
| 주말 | 상차 희망일이 토·일요일 |
| 수작업 상하차 | 상하차 방법이 수작업 |
| 긴급 | 상차 희망 시각이 등록 시각으로부터 24시간 이내 |

**차종과 단가표** (초기 데이터, 관리자가 수정 가능)

| 차종 코드 | 차종 | 최대 적재(kg) | 기본요금(원) | km당 단가(원) |
| --- | --- | --- | --- | --- |
| `TON_1` | 1톤 | 1,000 | 30,000 | 1,000 |
| `TON_2_5` | 2.5톤 | 2,500 | 50,000 | 1,400 |
| `TON_5` | 5톤 | 5,000 | 80,000 | 1,900 |
| `TON_11` | 11톤 | 11,000 | 130,000 | 2,600 |
| `TON_25` | 25톤 | 25,000 | 200,000 | 3,500 |

위 금액은 시연용으로 임의로 정한 값이고 실제 시세가 아닙니다. 단가표는 `fare_rate` 테이블(차종별 1행), 할증률은 `fare_surcharge` 테이블에 두고 `data.sql`로 초기화합니다.

**제공 방식**: `POST /api/fares/estimate`에 출발지·도착지 좌표, 중량, 차종(선택), 할증 조건을 보내면 거리, 추천 차종, 추천 운임, 계산 내역을 돌려줍니다. 오더에는 등록 시점의 거리와 추천 운임도 함께 저장해, 화주가 입력한 운임과 비교할 수 있게 합니다.

## 5. 차주 매칭

차주는 차종별 탭으로 나뉜 의뢰 목록에서 직접 골라 수락하고, 첫 탭은 '내 차량 맞춤'입니다. 자동 배정은 하지 않습니다.

**차량 등록**

- 차주는 가입 직후 또는 마이페이지에서 차량(차종 코드, 차량번호, 적재함 형태)을 등록합니다. 차량이 없으면 의뢰를 수락할 수 없습니다.
- 첫 버전은 차주 한 명에 차량 한 대입니다. 테이블은 `vehicle`로 따로 두어 여러 대로 늘리기 쉽게 합니다.

**의뢰 목록**

- 탭 구성: 내 차량 맞춤 | 1톤 | 2.5톤 | 5톤 | 11톤 | 25톤
- 보이는 오더: 등록됨 상태만, 희망 배송일이 가까운 순
- '내 차량 맞춤' = 요구 차종이 내 차량 차종과 같은 오더
- 목록 API는 `GET /api/orders/open?vehicleType=TON_5&page=0` 하나이고, 맞춤 탭은 프론트가 내 차종을 넣어 부릅니다.

**차종 불일치 경고**

- 요구 차종과 내 차종이 다르면, 수락 버튼을 눌렀을 때 "보유 차량(5톤)과 요구 차종(1톤)이 다릅니다. 계속하시겠습니까?" 확인창을 띄웁니다.
- 서버도 한 번 더 확인합니다. 불일치인데 요청에 `confirmMismatch=true`가 없으면 거절하고 불일치 오류 코드를 돌려줍니다. 프론트는 이 오류를 받으면 경고창을 띄웁니다.
- 화물 중량이 내 차량의 최대 적재량을 넘는 경우도 거부하지 않고 경고만 띄웁니다. 경고창에 "화물 중량(5,000kg)이 차량 최대 적재량(1,000kg)을 넘습니다"를 함께 보여주고, 확인 방식은 차종 불일치와 같은 `confirmMismatch=true`입니다. *(팀 결정)*

**동시 수락 방지**

- 두 차주가 같은 오더를 거의 동시에 수락하면 한 명만 성공하고, 다른 한 명은 "이미 배차된 의뢰입니다" 오류를 받습니다.
- 방식은 JPA 낙관적 락(`@Version`)을 제안합니다. 두 번째 커밋에서 충돌 예외가 나면 위 오류로 바꿉니다.
- 테스트: 스레드 10개가 한 오더를 동시에 수락했을 때 성공이 정확히 1건인지 확인하는 통합 테스트를 반드시 둡니다. 다른 방식(비관적 락, 조건부 UPDATE)과 비교한 결과를 README에 남기면 면접에서 설명하기 좋습니다.

**본 뒤 수정된 오더 수락** *(제가 임의로 정한 것)*

- 차주가 목록을 본 뒤 화주가 운임이나 내용을 고치면, 차주가 바뀐 내용을 모른 채 수락하지 못하게 막습니다.
- 목록·상세 응답에 오더의 `version`을 포함하고, 수락 요청에 그 값을 담아 보냅니다. 서버의 값과 다르면 `ORDER_CHANGED` 오류로 거부하고, 프론트는 바뀐 내용을 다시 보여줍니다.
- 같은 `@Version` 값을 쓰므로 동시 수락 방지와 한 장치로 처리됩니다.

## 7. 기술 구조

백엔드는 단일 Spring Boot 앱이고, 도메인 폴더 안에 팀이 익숙한 계층 구조(controller / service / repository)를 둡니다.

| 구분 | 사용 기술 |
| --- | --- |
| 백엔드 | Java 21(Gradle toolchain으로 고정), Spring Boot 3.2 이상, Spring Data JPA, Spring Security + JWT, springdoc-openapi(Swagger) |
| 프론트 | React(Vite), React Router, axios. 상태 관리와 UI 라이브러리는 팀이 착수 전에 하나로 정한다 |
| DB | MySQL 8, 드라이버 `mysql-connector-j` |
| 외부 API | 다음 우편번호 서비스(주소 검색), 카카오 로컬(좌표 변환), 카카오모빌리티 길찾기(거리) |
| 품질 도구 | Spotless(백엔드 포맷), ArchUnit(패키지 규칙 테스트), JUnit 5, ESLint + Prettier(프론트), GitHub Actions |

**패키지 구조**

```
com.example.freight
├─ global/        config(Security, JWT, Swagger), exception, common(공통 응답, BaseEntity)
├─ member/        controller / service / repository / entity / dto
├─ vehicle/
├─ fare/
├─ order/
├─ matching/
├─ delivery/      진행·분쟁
└─ payment/       에스크로 결제(보관·지급·환불)
```

**도메인 사이 규칙**

- 다른 도메인의 기능이 필요하면 그 도메인의 service를 호출한다. 다른 도메인의 repository를 직접 쓰지 않는다.
- `Order` 엔티티와 상태 enum은 `order` 도메인이 갖는다. `matching`과 `delivery`는 `OrderService`가 내보인 메서드로만 상태를 바꾼다.
- 컨트롤러는 엔티티를 반환하지 않고 DTO를 반환한다.

**공통 응답 형식**

```json
{ "success": false, "data": null, "error": { "code": "ORDER_ALREADY_ASSIGNED", "message": "이미 배차된 의뢰입니다" } }
```

오류 코드는 `global/exception/ErrorCode` enum 한 곳에 모으고, 각 담당자가 자기 도메인 코드를 추가합니다.

**로컬 실행 환경**

- 각자 PC에 MySQL을 설치하고 DB 이름과 계정을 똑같이 맞춘다(예: `freight` / `freight`). 접속 정보는 `application-local.yml`에 둡니다.
- 테이블은 JPA가 만든다(`ddl-auto: update`). 테스트 데이터(화주·차주·관리자 계정, 단가표, 샘플 오더)는 `data.sql`로 Git에 올린다.
- 외부 API 키는 Git에 올리지 않는다. `application-local.yml`은 `.gitignore`에 넣고, `application-local.example.yml`만 공유한다.
- 프론트는 `npm run dev`로 띄우고, Vite 프록시로 `/api`를 `localhost:8080`에 보낸다.

## 8. 검토한 방식과 선택 이유

도메인 폴더 안에 계층 구조를 두는 단일 앱을 골랐습니다. 5명이 기능 단위로 나눠 동시에 작업하면서도, 폴더 안은 팀이 학습해 온 구조 그대로이기 때문입니다.

| 방식 | 장점 | 단점 | 결정 |
| --- | --- | --- | --- |
| 도메인 폴더 + 내부 계층 구조 | 담당 범위가 폴더로 나뉘어 Git 충돌이 적다. 담당자가 백엔드부터 프론트까지 한 기능을 끝까지 만든다 | 첫 주 공통 기반(특히 상태 전이)이 흔들리면 모두가 영향을 받는다 | **선택** |
| 계층별 패키지(controller / service / repository 최상위) | 팀에 가장 익숙하다 | 5명이 같은 폴더를 동시에 고쳐 충돌이 잦고, 기능 단위 분담과 맞지 않는다 | 제외 |
| 멀티 모듈 / 마이크로서비스 | 포트폴리오에서 이름값이 있다 | 한 달 안에 서비스 간 통신과 데이터 일관성까지 다루기 어렵다. 오더 상태를 여러 도메인이 함께 바꾸는 구조에서는 오히려 복잡해진다 | 제외 |

이 밖의 주요 결정과 이유는 이렇습니다.

- **운임 = 화주 입력 + 추천 운임**: 입찰·협상 흐름 없이도 화주가 적정 금액을 알 수 있다.
- **수령 확인 단계(B 방식)**: 수령 확인이 곧 차주 지급 시점이 된다. 화주가 등록 때 미리 결제하므로(에스크로) 차주의 운임 미지급 위험도 없다. 차주 버튼만 있는 방식(A)은 허위 완료를 막을 수 없고, 증빙 사진(C)은 파일 저장까지 늘어나 확장으로 미룬다.
- **반응형 웹**: 실제 서비스를 하지 않으므로 앱까지는 필요 없다.
- **차종 불일치 = 경고 후 허용**: 큰 차가 작은 화물을 싣는 것은 실제로도 있는 일이라 막지 않는다.

## 9. 팀 작업 방식

5명이 도메인을 하나씩 맡아 백엔드를 먼저 끝내고, 같은 사람이 그 기능의 프론트까지 만듭니다. 첫 주 공통 기반은 다 같이 만듭니다.

| 담당 | 도메인 | 백엔드 | 화면 |
| --- | --- | --- | --- |
| A | member, global 인증 | 회원가입·로그인, JWT, 역할 권한 | 로그인, 회원가입, 관리자 회원 관리 |
| B | vehicle, fare | 차량 등록, 단가표, 추천 운임 계산, 지도 API 연동 | 차량 등록, 추천 운임 영역, 관리자 단가표 |
| C | order | 오더 엔티티와 상태 전이 메서드, 등록·조회·수정·취소, 상태 이력 | 오더 등록, 내 오더 목록·상세, 관리자 오더 관리 |
| D | matching | 의뢰 목록(차종 필터), 수락, 동시 수락 방지, 불일치 검사 | 차주 의뢰 목록(탭, 경고창) |
| E | delivery | 상차·하차, 수령 확인, 자동 확인 스케줄러, 분쟁, payment 도메인(보관·지급·환불, 더미 PG) | 차주 내 운송, 오더 상세의 진행 버튼, 관리자 분쟁 처리 |

C가 만드는 `Order`와 상태 전이를 D와 E가 씁니다. 그래서 상태 전이 메서드의 이름과 시그니처는 첫 주에 확정하고, 내부 구현은 C가 채웁니다.

**첫 주에 함께 만드는 것**

- [ ] 저장소 생성, 브랜치 규칙(`main` 보호, 기능 브랜치 + PR, 승인은 필수 아님)
- [ ] ERD: 회원, 차량, 오더, 상태 이력, 단가표, 할증률
- [ ] 오더 상태 enum과 상태 전이 메서드 시그니처
- [ ] global: 공통 응답, `ErrorCode`, 전역 예외 처리, BaseEntity(생성·수정 시각)
- [ ] Security + JWT 뼈대와 역할 권한 규칙
- [ ] 견본 도메인 하나 완성 (member 추천: controller부터 테스트까지)
- [ ] `AGENTS.md`, Spotless, ArchUnit, ESLint·Prettier, GitHub Actions 설정
- [ ] `data.sql` 테스트 데이터, `application-local.example.yml`
- [ ] React 프로젝트 뼈대: 라우터, axios 인스턴스(토큰 첨부), 레이아웃

**브랜치 전략** *(제안)*

`main`과 `develop` 두 개의 고정 브랜치를 두고, 모든 작업은 `develop`에서 따 낸 짧은 작업 브랜치에서 합니다. 배포가 없으므로 release·hotfix 브랜치는 두지 않습니다.

| 브랜치 | 용도 | 규칙 |
| --- | --- | --- |
| `main` | 매주 끝날과 최종 발표 시점의 완성본 | 직접 push 금지. `develop`에서만 PR로 합치고, 합칠 때 `v0.1`, `v0.2` … 태그 |
| `develop` | 팀 전체 작업을 모으는 통합 브랜치 | 직접 push 금지. PR + CI 통과 시에만 합침. 승인은 필수가 아니어서 올린 사람이 직접 합친다 |
| `feat/<도메인>-<기능>` | 기능 개발 (예: `feat/order-create`, `feat/matching-accept`) | `develop`에서 따고 하루~이틀 안에 PR. 기능 하나씩 작게 나눈다 |
| `fix/<내용>` | 버그 수정 | 위와 같음 |
| `chore/<내용>` | 설정, 문서, 빌드 (예: `chore/archunit`) | 위와 같음 |

- **합치는 방식**: PR은 Squash merge로 합쳐 `develop` 이력을 기능 단위 한 줄씩으로 유지합니다. 합친 브랜치는 삭제합니다.
- **충돌 줄이기**: 작업 전마다 `develop`을 받아 자기 브랜치에 합칩니다. `global` 폴더나 `ErrorCode`처럼 모두가 고치는 파일은 기능 PR과 분리해 작은 PR로 먼저 합칩니다.
- **커밋 메시지**: `feat: 오더 등록 API 추가`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:` 접두어를 씁니다.
- **GitHub 설정**: `main`과 `develop`에 브랜치 보호 규칙(PR 필수, 승인 0명, CI 통과 필수)을 겁니다. PR 템플릿에는 '무엇을 바꿨나 / 어떻게 확인했나 / 다른 도메인에 영향' 세 칸을 둡니다.

## 10. AI 작업 규칙과 AGENTS.md

팀원마다 AI 모델이 달라도 같은 규칙을 읽게 하고, 어기면 기계가 걸러내게 합니다. 앞의 것일수록 효과가 큽니다.

1. **공통 지시 파일**: 저장소 루트에 `AGENTS.md`를 둡니다. Codex, Copilot, Antigravity는 AGENTS.md를 직접 읽습니다. Claude Code는 `CLAUDE.md`를 먼저 읽으므로, 그 파일에는 `@AGENTS.md`로 AGENTS.md를 불러오는 내용만 씁니다.
2. **견본 도메인**: AI에게 "member 도메인과 같은 방식으로 만들어"라고 시킵니다.
3. **자동 검사**: Spotless·Prettier로 형식, ArchUnit으로 패키지 규칙, 핵심 로직 테스트, PR마다 GitHub Actions로 전부 실행합니다.
4. **사람 리뷰**: 소규모 팀이라 PR 승인은 필수가 아닙니다. 올린 사람이 직접 합치고, 봐 줄 사람이 필요하면 PR에서 리뷰어를 지정합니다.

**superpowers 플러그인** *(팀 결정: 전원 설치, 사용 규칙은 제안)*

팀원 모두 superpowers를 설치해 AI가 같은 작업 순서(설계 → 계획 → 테스트 먼저 구현 → 검증 → 리뷰)를 따르게 합니다. superpowers는 Claude Code와 Codex 등 일부 도구만 지원하므로, 각자 쓰는 도구가 지원하는지 첫 주에 확인합니다. 지원하지 않는 도구를 쓰는 팀원도 AGENTS.md는 똑같이 따릅니다.

| 단계 | 쓰는 스킬 | 규칙 |
| --- | --- | --- |
| 기능 설계 | brainstorming | 이 설계 문서가 기준입니다. 기능별 브레인스토밍은 문서가 비워 둔 부분만 정하고, 문서와 다른 결론이 나오면 팀에 공유해 문서를 먼저 고칩니다 |
| 계획 | writing-plans | 계획 파일은 `docs/superpowers/plans/`에 커밋합니다. 다른 팀원도 누가 무엇을 하는지 볼 수 있습니다 |
| 구현 | test-driven-development | 상태 전이, 동시 수락, 추천 운임은 반드시 테스트 먼저 작성합니다 |
| 완료 전 | verification-before-completion | `./gradlew spotlessApply test`와 `npm run lint` 결과를 확인한 뒤에만 완료라고 합니다 |
| PR 전 | requesting-code-review | AI 리뷰를 한 번 돌린 뒤 PR을 올립니다. 사람 승인은 필수가 아닙니다 |

스킬이 만드는 설계·계획 문서의 기본 저장 위치는 `docs/superpowers/` 아래입니다. 이 설계 문서는 `docs/superpowers/specs/2026-11-02-freight-platform-design.md`에 둡니다.

**AGENTS.md 초안** (첫 주에 팀이 다듬어 저장소에 넣습니다)

```markdown
# AGENTS.md

이 파일은 이 저장소에서 일하는 모든 AI 도구가 따르는 규칙이다.
설계는 docs/superpowers/specs/2026-11-02-freight-platform-design.md를 기준으로 한다.

## 프로젝트
- 화물 중개 웹 플랫폼. 백엔드 Spring Boot 3 / Java 21 / JPA / MySQL, 프론트 React(Vite).
- 역할: SHIPPER(화주), DRIVER(차주), ADMIN(관리자).

## 패키지 구조
- com.example.freight.<도메인>.{controller,service,repository,entity,dto}
- 도메인: member, vehicle, fare, order, matching, delivery, payment. 공통은 global.
- 새 도메인 코드는 member 도메인을 견본으로 같은 모양으로 만든다.

## 반드시 지킬 것
- 다른 도메인의 repository를 직접 쓰지 않는다. 필요하면 그 도메인의 service를 호출한다.
- 오더 상태는 Order 엔티티의 상태 전이 메서드로만 바꾼다. setStatus를 만들거나 부르지 않는다.
- 컨트롤러는 엔티티가 아니라 DTO를 반환한다. 응답은 공통 응답 형식(ApiResponse)을 쓴다.
- 예외는 BusinessException(ErrorCode)로 던지고, 오류 코드는 ErrorCode enum에 추가한다.
- 상태 전이, 동시 수락, 추천 운임 코드를 바꾸면 관련 테스트도 함께 고친다.
- 비밀번호, API 키를 코드나 커밋에 넣지 않는다.
- 맡은 도메인 밖의 파일(global 포함)을 고칠 때는 PR 설명에 이유를 적는다.

## 이름 규칙
- API: /api/<복수형 자원> (예: /api/orders/{id}/accept), 관리자는 /api/admin/...
- DTO: <동작><대상>Request / <대상>Response (예: CreateOrderRequest, OrderResponse)
- 테이블·컬럼: snake_case, 엔티티 필드: camelCase

## superpowers
- 설계 기준은 docs/superpowers/specs/2026-11-02-freight-platform-design.md 다. 기능별 브레인스토밍은 이 문서가 비워 둔 부분만 정한다.
- 계획은 docs/superpowers/plans/ 에 커밋한다.
- 상태 전이, 동시 수락, 추천 운임은 테스트를 먼저 쓴다.

## 작업 전후 확인
- 커밋 전에 ./gradlew spotlessApply test 가 통과해야 한다.
- 프론트는 npm run lint 가 통과해야 한다.
```

## 11. 범위 밖, 구현자 판단, 임의로 정한 것

**확장 후보** (구조는 이것들을 나중에 붙일 수 있게 둔다)

- 상차·하차 증빙 사진 (C 방식)
- 차주 운임 제안·입찰
- 차주 1인 여러 차량
- 문자·푸시 알림, 실시간 위치
- 평점·후기

**구현자가 정해도 되는 것**

- 화물 정보의 세부 입력 항목 (단, 주소와 중량 kg은 필수)
- 화면 디자인, 상태 관리·UI 라이브러리 (팀이 하나로 통일)
- 목록의 페이지 크기, 검색 조건의 세부
- JWT 만료 시간과 갱신 방식

**제가 임의로 정한 것** (팀이 확인해 주세요)

- 차종 5개(1 / 2.5 / 5 / 11 / 25톤)와 단가표 금액
- 할증 4가지(야간 22~06시, 주말, 수작업 상하차, 긴급)와 합산 방식, 1,000원 단위 반올림
- 지도 API로 카카오 계열 사용, 실패 시 직선거리 × 1.3
- 자동 확인 24시간, 스케줄러 10분 간격
- 배차 후 취소는 관리자만 가능
- 동시 수락을 낙관적 락으로 처리
- 차주 1인 1차량, 차량 없으면 수락 불가
- 담당 A~E의 도메인 배정과 견본 도메인으로 member 선택
- Spring Boot 3.2 이상, Vite (Java 21은 팀 결정)
