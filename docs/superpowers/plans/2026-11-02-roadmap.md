# 화물운송플랫폼 전체 로드맵

**Spec:** 화물운송플랫폼 설계 문서 — https://claude.ai/artifact/LENc6NFFQ9vxeBMQ7rdpgb (저장소에서는 `docs/superpowers/specs/2026-11-02-freight-platform-design.md`)

설계 문서를 한 번에 구현하는 계획 하나로 쓰지 않고, 첫 주 공통 기반 계획 하나와 담당별 도메인 계획 다섯 개로 나눈다. 공통 기반 계획은 `2026-11-02-foundation.md`에 있다. 도메인 계획은 각 담당이 둘째 주 시작 전에 superpowers의 writing-plans로 작성하고 `docs/superpowers/plans/<날짜>-<도메인>.md`로 커밋한다. 이 문서는 그때 서로 맞춰야 하는 **도메인 사이의 약속(인터페이스)**과 일정을 정한다.

## 도메인 사이의 약속

이름과 시그니처는 여기 적힌 대로 만든다. 상대 도메인이 아직 합쳐지지 않았으면 테스트에서는 Mockito로 대신하고, 합쳐진 뒤 통합 테스트로 바꾼다. 바꿔야 하면 PR을 올리기 전에 팀에 공유하고 이 문서를 먼저 고친다.

**member (A, foundation에서 완성)**
- `MemberService.getById(Long id): Member`
- `GET /api/admin/members`, `GET /api/admin/members/{id}`, `PATCH /api/admin/members/{id}/status` `{ status }` — 상태는 `ACTIVE`, `SUSPENDED`. 정지 계정의 로그인은 `ACCOUNT_SUSPENDED`로 막고, 발급된 토큰은 만료까지 둔다
- (여유 시) `GET /api/admin/dashboard` — 오늘 등록·배차·완료 건수와 어제 건수, 미배차 건수, 처리할 분쟁, 상차일이 가까운 미배차. 다른 도메인 값은 그 도메인 service로 읽는다

**vehicle·fare (B)**
- `VehicleService.findByDriverId(Long driverId): Optional<Vehicle>`
- `FareService.estimate(FareEstimateCommand c): FareEstimate`
  - `record FareEstimateCommand(double pickupLat, double pickupLng, double dropoffLat, double dropoffLng, int weightKg, VehicleType vehicleType /* null이면 추천 */, LocalDateTime pickupAt, LoadingMethod loadingMethod, LocalDateTime requestedAt)`
  - `record FareEstimate(double distanceKm, boolean isDistanceEstimated, VehicleType recommendedVehicleType, long baseFare, long distanceFare, long surchargeAmount, long recommendedFare, List<String> appliedSurcharges)` — 화면이 계산 내역과 '거리는 추정값입니다' 안내를 그릴 수 있게 한다
  - 추천 차종 = `maxLoadKg >= weightKg`인 가장 작은 차종. 25,000kg 초과면 `TON_25`(경고 표시는 화면에서)
  - 할증 판정(설계 문서 4장): 야간 = `pickupAt` 시각 22~06시, 주말 = 토·일, 수작업 = `loadingMethod == MANUAL`, 긴급 = `pickupAt - requestedAt <= 24h`. 할증률은 더한다. 결과는 1,000원 단위 반올림
  - 거리 = 카카오모빌리티 길찾기. 실패하거나 키가 없으면 하버사인 직선거리 × 1.3
- `GeocodingService.geocode(String address): Coordinates` — 카카오 로컬 API. 주소 검색 창은 프론트의 다음 우편번호 서비스
- 공개 API: `POST /api/fares/estimate`
- 단가표 API는 기본요금, km당 단가, 할증률만 바꾼다. 최대 적재량은 `VehicleType`에 고정된 값이다
- 프론트 공통 컴포넌트 `OrderMap`: 정확한 좌표 두 개를 받으면 두 지점을, 시·구 이름 두 개를 받으면 대략 영역을 그린다. 지도 키는 `VITE_KAKAO_MAP_KEY`에서 읽고, 불러오지 못하면 안내만 보여준다

**order (C)**
- `OrderService.changeStatus(Long orderId, Long actorId, String memo, BiFunction<Order, Member, StatusChange> transition): StatusChange`
  - 오더와 행위자를 읽고, `transition`(예: `(o, m) -> o.startTransit(m)`)을 실행한 뒤 `order_status_history`에 한 줄 남긴다. D·E는 상태를 바꿀 때 반드시 이것을 쓴다.
  - 시스템 행동(자동 확인)은 `actorId = null`
- `OrderService.getOrder(Long orderId): Order` (없으면 `ORDER_NOT_FOUND`)
- API: `POST /api/orders`, `GET /api/orders`, `GET /api/orders/{id}`, `PUT /api/orders/{id}`, `POST /api/orders/{id}/cancel`, `GET /api/admin/orders`, `GET /api/admin/orders/{id}`, `POST /api/admin/orders/{id}/cancel`
- 오더 상세 응답에 배정 차주의 이름, 연락처, 차종, 적재함, 차량번호와 `autoConfirmAt`, `driverCancelableUntil`을 담는다
- 내용 수정은 `REGISTERED → REGISTERED`로 이력에 남기고, 운임이 바뀌면 메모에 바뀌기 전후 금액을 적는다
- `OrderService.countDriverCancellations(Long driverId): long` — 이력에서 행위자가 그 차주이고 `ASSIGNED → REGISTERED`인 건수
- 오더 상세 응답의 개인정보 규칙: 상세주소와 연락처는 화주 본인, 배정된 차주(ASSIGNED 이후), 관리자에게만 보낸다
- 화주 오더 목록: `pickupAt`이 지났는데 REGISTERED인 오더에 '미배차' 표시. 상세: 마지막 이력이 차주 배차 취소면 '차주가 배차를 취소했습니다'와 사유 표시
- 결제 연동: 등록 시 `PaymentService.hold`, 수정으로 운임이 바뀌면 `PaymentService.adjust`, 취소(화주·관리자) 시 `PaymentService.refund`. 오더 변경과 같은 트랜잭션

**matching (D)**
- `GET /api/orders/open?vehicleType=&page=` — REGISTERED만, `pickupAt` 가까운 순, 주소는 `region`만
- `GET /api/orders/open/{id}` — 수락 전 의뢰 상세. REGISTERED만, 주소는 `region`만, 상세주소·연락처·좌표는 보내지 않는다. 이미 REGISTERED가 아니면 `ORDER_ALREADY_ASSIGNED`
- `POST /api/orders/{id}/accept` `{ version, confirmMismatch }`
  - 차량이 없으면 `VEHICLE_REQUIRED`
  - `version`이 다르면 `ORDER_CHANGED`
  - 차종이 다르거나 `weightKg > maxLoadKg`이고 `confirmMismatch`가 아니면 `VEHICLE_MISMATCH`(응답에 내 차종, 요구 차종, 중량, 최대 적재량을 담아 화면이 경고창을 띄울 수 있게)
  - 낙관적 락 충돌이나 이미 REGISTERED가 아니면 `ORDER_ALREADY_ASSIGNED`
- `POST /api/orders/{id}/cancel-assignment` `{ reason }` (reason 필수)
- 이 도메인이 `ErrorCode`에 추가: `VEHICLE_REQUIRED`, `VEHICLE_MISMATCH`, `ORDER_CHANGED`, `ORDER_ALREADY_ASSIGNED`
- 필수 테스트: 스레드 10개 동시 수락 시 성공 정확히 1건(H2가 아니라 로컬 MariaDB로도 한 번 확인), 비관적 락·조건부 UPDATE와 비교한 결과를 README에 기록

**delivery·payment (E)**
- `PaymentService.hold(Long orderId, long amount)`, `adjust(Long orderId, long newAmount)`, `release(Long orderId)`, `refund(Long orderId)` — 상태 규칙은 `HELD → RELEASED | REFUNDED`, 한 번 끝난 결제는 다시 바뀌지 않음(`PAYMENT_ALREADY_SETTLED`). 거래는 `payment_transactions`에 건별 기록
- `PaymentGateway` 인터페이스(`charge`, `refund`, `payout`)와 `DummyPaymentGateway`(항상 성공)
- `POST /api/orders/{id}/pickup`, `/dropoff`, `/confirm`, `/report` `{ reason }`
- `GET /api/admin/disputes`, `GET /api/admin/disputes/{orderId}`
- `POST /api/admin/disputes/{orderId}/resolve` `{ resolution: PAY_DRIVER | REFUND_SHIPPER, memo }` — `memo`는 필수이고 상태 이력에 남는다
- `GET /api/jobs?status=&page=`, `GET /api/jobs/{orderId}`(배정된 차주만), `GET /api/payouts?page=` — 내 운송, 운송 상세, 지급 내역
- `GET /api/orders/{id}/payment` — 결제 상태와 건별 내역. 화주 본인과 관리자만
- 운송완료가 되는 모든 경로(확인, 자동 확인, 분쟁 지급)는 같은 트랜잭션에서 `release`, 분쟁 취소는 `refund`
- 스케줄러: 10분마다 `AWAITING_CONFIRM` 중 `droppedOffAt + app.order.auto-confirm-hours` 지난 오더를 `autoConfirm`
- 필수 테스트: 화주 확인과 자동 확인이 동시에 일어나도 `PAYOUT` 거래가 1건뿐, 모든 취소 경로 끝에 결제가 `REFUNDED`, 모든 완료 경로 끝에 `RELEASED`

## 최종 확인 시나리오 (4주차)

1. 화주가 오더를 등록하면 추천 운임이 보이고, 결제가 HELD가 된다.
2. 5톤 차주의 '내 차량 맞춤' 탭에는 5톤 오더만 보이고, 주소는 시·구까지만 보인다.
3. 1톤 차주가 5,000kg 오더를 수락하려 하면 경고창이 뜨고, 확인하면 수락된다.
4. 두 차주가 동시에 수락하면 한 명만 성공한다.
5. 차주가 목록을 본 뒤 화주가 운임을 바꾸면, 그 차주의 수락은 '내용이 변경됨'으로 거부된다.
6. 상차 3시간 전 차주 취소는 되고, 1시간 전 취소는 거부된다.
7. 하차 후 화주가 확인하면 결제가 RELEASED가 된다. 확인하지 않으면 (설정을 1분으로 줄여) 자동으로 RELEASED가 된다.
8. 문제 신고 후 관리자가 환불을 고르면 오더는 CANCELLED, 결제는 REFUNDED가 된다.
9. 다른 차주의 오더를 상차 처리하려 하면 거부된다.
10. 휴대폰 폭(360px)에서 화주·차주 화면이 가로 스크롤 없이 쓰인다.
