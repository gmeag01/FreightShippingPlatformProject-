# 4주차 통합 점검 결과

로드맵 4주차 완료 기준인 '최종 확인 시나리오 전부 통과'를 확인한 기록이다. 2주차에는 API로 확인했고([2주차 결과](2026-11-05-week2-integration-test.md)), 이번에는 같은 시나리오를 브라우저 화면으로 다시 실행했다.

- 실행일: 2026-11-11
- 기준 코드: `develop` 37b2a47 (PR #54까지)
- 환경: 백엔드 로컬 MariaDB 12.3.3(개발 DB), 프론트 Vite 개발 서버, 앱 안 브라우저(1280px, 360px)

## 결론

시나리오 10번(휴대폰 폭)이 실패해 PR #56에서 고쳤다. 고친 뒤에는 1~10번 모두 통과했다. 8번의 관리자 환불은 화면으로는 확인하지 못했고(아래 '확인하지 않은 것' 참고) 자동 테스트로 확인했다.

## 시나리오별 결과 (화면)

| 번호 | 시나리오 | 결과 | 확인한 방법 |
| --- | --- | --- | --- |
| 1 | 등록 시 추천 운임 표시, 결제 HELD | 통과 | 화주 오더 등록 화면. 5톤·5,000kg 서울 중구 → 부산 연제구, 398.8km, 추천 운임 1,089,000원(긴급 할증). 등록 후 상세에 '운임 보관 중' |
| 2 | 5톤 차주 '내 차량 맞춤' 탭에 5톤만, 주소는 시·구까지 | 통과 | driver1(5톤) 의뢰 목록. 5톤 오더 3건만, 주소는 '서울 중구' 형태 |
| 3 | 1톤 차주가 5,000kg 오더 수락 시 경고 후 수락 | 통과 | driver2(1톤) 의뢰 상세에서 수락 → '적재량을 넘는 화물입니다' 경고창 → '확인 후 수락'으로 배차 완료, 상세주소 표시 |
| 4 | 동시 수락 시 한 명만 성공 | 통과 (자동 테스트) | 화면으로 동시 클릭을 재현할 수 없어 `accept_byTwoDriversAtOnce_onlyOneSucceeds`, `MatchingConcurrencyTest`로 확인 |
| 5 | 목록을 본 뒤 운임이 바뀌면 수락 거부 | 통과 | driver1이 의뢰 상세를 연 뒤 화주가 운임을 700,000 → 750,000원으로 수정. 수락하면 '의뢰 내용이 바뀌었습니다' 창에 바뀐 운임 표시 |
| 6 | 상차 3시간 전 취소 가능, 1시간 전 거부 | 통과 | 3시간 뒤 오더는 내 운송 화면에서 사유 입력 후 취소, 화주 상세 이력에 사유 표시. 1시간 뒤 오더는 취소 버튼 비활성, API 직접 호출도 409 `DRIVER_CANCEL_CUTOFF_PASSED` |
| 7 | 화주 확인 또는 자동 확인으로 RELEASED | 통과 (수령 확인은 화면) | 차주 화면에서 상차·하차 → 화주 '수령 확정' → '운송 완료', 결제 '기사 지급 완료'(결제·기사 지급 2건). 자동 확인은 2주차에 실제 스케줄러로 확인했고 이번에는 `autoConfirm_afterDeadline_releasesFareOnce`로 확인 |
| 8 | 문제 신고 후 관리자 환불이면 CANCELLED, REFUNDED | 신고는 화면, 환불은 자동 테스트 | 화주 '문제 신고' → '분쟁 처리 중'. 관리자 처리는 `resolveDispute_refundShipper_cancelsOrderAndRefunds`로 확인 |
| 9 | 다른 차주의 오더 상차 처리 거부 | 통과 | driver1이 driver2의 오더에 상차 요청 → 403 `NOT_ORDER_OWNER`. 화면에는 남의 운송이 나오지 않는다 |
| 10 | 360px에서 화주·차주 화면 가로 스크롤 없음 | 수정 후 통과 | 아래 '발견한 문제' 1번 |

10번은 각 화면을 360px 폭으로 열고 `document.documentElement.scrollWidth`가 360인지 확인했다. 확인한 화면은 `/shipper/orders`, `/shipper/orders/new`, `/shipper/orders/:id`, `/shipper/orders/:id/edit`, `/driver/orders`, `/driver/orders/:id`, `/driver/jobs`, `/driver/jobs/:id`, `/driver/vehicle`이다. 의뢰 목록의 차종 탭은 탭 틀 안에서만 가로로 스크롤된다(ui-guide.md 허용).

## 발견한 문제

| 문제 | 상태 | 담당 |
| --- | --- | --- |
| 360px에서 화주·차주 모든 화면이 9px 넘쳐 가로 스크롤이 생겼다. 공통 머리말의 메뉴가 줄어들지 못해 로그아웃 버튼이 밀렸다 | PR #56. 휴대폰 폭에서는 시안대로 메뉴를 둘째 줄로 내린다 | 공통 |
| 관리자 대시보드(`GET /api/admin/dashboard`, `/admin` 화면)가 아직 없다. `/admin`은 아직 `PlaceholderPage`다 | 미해결. 로드맵 4주차 작업이다 | A |
| 2주차 기록의 `GET /api/fares/geocode` 서울시청 좌표 반환 문제 | 이번에 다시 확인하지 않았다 | B |

## 확인하지 않은 것

- 관리자 화면에서의 분쟁 환불(시나리오 8 후반). 로컬 개발 DB의 1번 관리자 계정이 시드와 다른 이메일·비밀번호로 바뀌어 있어 시드 계정(`admin@freight.test`)으로 로그인하지 못했다. 기존 계정은 건드리지 않았다. `data.sql`이 `INSERT IGNORE`라 다시 띄워도 고쳐지지 않는다
- 관리자 화면의 360px 폭 (시나리오 10은 화주·차주 화면만 다룬다)
- 지도. 이번 프론트 실행에는 `VITE_KAKAO_MAP_KEY`를 주지 않아 '구간 위치 안내'로 대신 표시되는 것만 확인했다
- 실제 휴대폰 기기. 브라우저의 360px 화면 크기로만 확인했다
